# 工具能力的持续优化

本文区分当前实现与后续建议，不是新增能力已经发布的承诺。当前开发分支有18项受限QQ工具、受管素材／可选视觉分析、收藏表情同步、三套随附stdio服务和八个接入预设；第三方预设不代表已经安装或登录。

## 优先完成真实链路验收

| 优先级 | 下一步 | 可核对的完成条件 |
| --- | --- | --- |
| P0 | Windows原生与Docker分别验证NapCat | 真实群中完成文字／真实@／引用、表情回应、图片、大小文件、转发及撤回本人消息；保存连接端版本、实际回执与未知结果处理记录 |
| P0 | 收藏表情与视觉的实号验收 | 核对当前QQ身份、允许CDN、重复与部分失败；本人主动识别一张素材，确认选定模型费用、缓存标签、取消及改版本后的拒绝保存 |
| P0 | 第三方预设逐项接通 | 固定版本自行安装、检查许可证与依赖、完成真实发现和最小授权；Telegram本人号、Discord Bot、Windows微信等身份分别核实，不能用模板生成成功代替登录成功 |
| P1 | 让工具选择更容易解释 | 从同名群友、多@、引用、连续短消息、同义标签等真实案例建立回归集，展示实际目标和使用来源；不清楚时澄清，保留拒绝与沉默 |
| P1 | 更好地管理素材 | 增加分页、批量标签和使用反馈；改善“适合／避免”的检索与排序，保留版本和人工纠正，避免靠文件名或固定触发词硬匹配全部语境 |
| P1 | 更清楚地展示任务与用量 | 将发现、读取、模型、传输、投递分阶段显示，关联真实回执与独立预算；不把排队或部分上传显示为已经发送 |
| P2 | 逐站点补充内容适配 | 先明确来源、读取覆盖和引用，再加专门读取器；动态或登录页面只在明确服务和独立会话下支持，不能把普通web_fetch当作完整浏览器 |
| P2 | OAuth与更多平台 | 在支持完整授权、撤销及会话生命周期后再开放Slack；实时入站平台需要独立适配器，不以MCP工具可调用代替消息监听 |
| P2 | 独立专用视觉通道 | 在保留单选主LLM的前提下，另行设计可选视觉设置、独立费用与撤销流程；当前版本只复用账号已启用的兼容API，DeepSeek-only仍用手工标签 |

## 保留的结构约束

人格和Skill负责表达与规划，工具负责有限业务能力，权限和执行回执由宿主决定。扩大能力时继续使用同一账号、实际QQ、群和会话范围，逐次复核授权；默认只读，外部写入和文件发送仍需明确许可。五项自然QQ互动的按群预授权不应逐渐演变为任意应用写入权限。

目录搜索和业务调用分别有界，所有模型轮都计入相应预算。更多工具不应直接扩大上下文或无限循环；先通过真实请求回归确认搜索与选择质量，再考虑是否调整预算。未知投递、取消和撤权保留终止语义，不能靠自动重试或换服务掩盖失败。

图片、网页、模型标注和外部服务返回都按不可信资料处理。视觉分析继续由本人显式触发；如以后增加群图理解，应另行设计逐群许可、图片获取来源、费用预算和保存期，不能沿用文字聊天开关自动上传群图片。

## 来源与审查方式

保留固定来源提交、接口事实、许可证和核查日期；区分“读过README／入口”“审过实现”“离线验证”“真实账号验收”。本项目当前QQ、网页与素材代码独立实现，未复制参考仓库的代理实现；第三方MCP仍使用自己的许可和依赖。每次更新以自己的测试及 [验证记录](VALIDATION.md) 为依据，不拿上游工具数量或功能介绍作为本项目完成证明。
